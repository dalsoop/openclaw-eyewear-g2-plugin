# 해결하지 못한 문제

## 기존 공개 이력의 이메일 메타데이터

- **현상**: 2026-10-30 전수 감사에서 PR #1 병합 커밋 `6d6b32041a3f2f5322fdd4c0890576e32db2bdd9`의 작성자·커미터 메타데이터 2건이 걸린다. 작성자의 개인 이메일은 이미 공개 이력에 노출돼 있다(값은 적지 않는다). 커미터는 GitHub 자체 계정이며 사용자별 noreply 주소가 아니다. 옛 OcuClaw blob 중복 발견은 공개 전 이력 정리로 사라졌다.
- **영향**: 새 PR이 기존 노출을 없애지는 못한다. `--all` 전수 감사는 이 두 발견을 계속 `FAIL`로 출력하고 1로 끝난다. PR 모드가 clean이어도 전수 감사가 clean이라는 뜻은 아니다.
- **지금 못 고치는 이유**: main 이력을 force-push하지 않는 정책이므로 기존 커밋 메타데이터를 다시 쓰지 않는다.
- **방법**: `docs/public-safety-baseline.json`에 SHA·규칙·사유만 기록했다(한 커밋의 두 발견). 2026-10-30 정책으로 PR 게이트는 PR이 더하는 커밋(`base..head`)과 인덱스·작업 트리를 검사하고, 전수 감사는 모든 ref를 검사한다. 기준선은 면제 목록이 아니다.

## PR 병합이 개인 이메일을 새로 남길 수 있다

- **현상**: GitHub의 PR 병합은 병합한 계정의 커밋 이메일을 새로 쓴다. merge·squash는 새 커밋의 작성자, rebase는 PR 커밋 각각의 커미터다. 2026-10-30 `gh pr merge --author-email`에 GitHub noreply 주소를 주자 GitHub가 "Invalid email address"로 거부했다. 이는 병합 계정의 이메일 비공개 설정이 꺼져 있다는 신호다(PR #1 병합 작성자도 개인 주소였다).
- **영향**: 이 상태로 병합하면 개인 이메일이 공개 이력에 새로 남는다. 전수 감사 출력은 값을 찍지 않으므로 이런 발견을 GitHub 자체 계정 커미터와 구별하려면 병합 직후 병합 범위를 따로 검사해야 한다.
- **지금 못 고치는 이유**: 계정의 이메일 비공개 설정은 계정 소유자가 정할 일이다. 저장소에서 바꿀 수 없고 main 직접 push는 금지다.
- **방법**: 계정 소유자가 GitHub Settings → Emails에서 "Keep my email addresses private"를 켜고 켰다고 확인해 주면(지금 gh 토큰으로는 이 설정을 읽을 수 없다) rebase로 병합한다. 직후 깨끗한 체크아웃에서 `scripts/public-safety-scan.sh --base <병합 전 main SHA> --head origin/main`이 clean인지 확인한다(`docs/operations.md`). 그 전에는 PR을 병합하지 않는다.

## opencodex 키가 자리 채움 값이다

- **현상**: `models.providers.opencodex.apiKey`에 짧은 자리 채움 값이 들어 있다. opencodex가 loopback 호출의 키를 검사하지 않아 지금은 모든 호출이 성공한다.
- **영향**: 리체의 사용량이 opencodex 사용 기록에서 다른 클라이언트와 구분되지 않는다. opencodex가 loopback 키 검사를 시작하면 리체의 대화, Hey Even, tick이 동시에 멈춘다.
- **지금 못 고치는 이유**: opencodex 키 발급은 사람만 할 수 있다.
- **방법**: 사용자가 전용 키를 발급해 `scripts/set-opencodex-key.sh`로 넣고 Gateway 재시작, `node scripts/check-live-tick-allowlist.mjs`로 확인.

## OcuClaw 업데이트에 패치가 함께 지워진다

- **현상**: OcuClaw를 업데이트하고 Gateway가 다시 뜨면 12개 항목이 모두 빠진다. 그 사이 Hey Even은 첫 조각만, tick은 "missing api key", 로그에 `sessions.compaction.list` 오류.
- **영향**: 사람이 알림을 보고 재적용할 때까지 Hey Even을 제대로 쓸 수 없다.
- **지금 못 고치는 이유**: 근본 수정은 OcuClaw 쪽 일이다. 버그 보고를 아직 하지 않았다.
- **방법**: OcuClaw에 세 버그(delta 전용 프레임 미처리, tick 키 조회에 문자열 전달, 미지원 메서드 호출)를 보고하고, 정식 수정이 나오면 해당 지점을 지운다.

## 패치된 플러그인의 출처 경고가 남는다

- **현상**: `plugins.allow`에 `ocuclaw`가 있어도 Gateway 시작마다 출처를 확인할 수 없다는 경고가 나온다.
- **영향**: 기능에는 영향이 없지만, 로그 점검 때 진짜 문제(로드 거부)와 섞여 보인다.
- **지금 못 고치는 이유**: 원본과 다른 파일을 OpenClaw가 검증할 방법이 없다. 패치를 하는 한 사라지지 않는다.
- **방법**: OcuClaw 정식 수정 후 패치를 지우면 사라진다.

## 내장 브라우저를 부르는 클라이언트가 "unknown method"를 받는다

- **현상**: `browser`가 허용 목록에서 빠져 있어 `browser.request`를 부르는 클라이언트가 있으면 Gateway 로그에 unknown method가 찍힌다.
- **영향**: 그 클라이언트의 브라우저 기능이 동작하지 않는다. 리체는 내장 브라우저를 쓰지 않으므로(웹 도구는 ego lite, 결정 0009) 영향은 로그 소음 수준이다.
- **지금 못 고치는 이유**: 어느 클라이언트가 부르는지 저장소 쪽에서 바꿀 수 없다. 내장 브라우저를 다시 켜는 것은 사용자 결정과 어긋난다.
- **방법**: 부르는 클라이언트를 찾아 그쪽 설정에서 브라우저 기능을 끈다.

## "잘 이해하지 못했습니다"

- **현상**: Hey Even에서 가끔 Even 앱이 "잘 이해하지 못했습니다"를 띄운다. 그때 서버에는 요청 기록이 없다(도착한 요청은 모두 성공).
- **영향**: 사용자는 리체가 실패한 것으로 느끼지만 서버에서 원인을 볼 수 없다.
- **지금 못 고치는 이유**: 요청이 서버에 닿기 전 Even 앱 안에서 생기는 일이다.
- **방법**: 알림음 뒤에 말하기, Even AI 언어가 한국어인지와 에이전트가 OcuClaw로 선택됐는지 확인. 계속되면 Even 쪽에 보고.
